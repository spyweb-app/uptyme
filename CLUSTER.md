# Cluster

Run UPTYME from several locations and combine the results, so a target only counts as down when enough independent locations agree. This cuts false positives from one bad network path.

- **Central node** - owns monitors, settings, channels and status pages, checks every monitor itself, and decides the final status.
- **Checker nodes** - receive the monitor list from central, probe targets from their own network, and report results back.

The two roles have very different network requirements:

| | **Central** | **Checker** |
|---|---|---|
| Reachable from the internet | **Yes** - unless the whole cluster is on one private network | **No** |
| Open inbound port | Yes - checkers must be able to reach it | No |
| Outbound access | Only for its own checks and alerts | **Yes** - to central and to the targets it probes |
| Where it can live | A VPS/server with a public address, or any box every checker can reach over LAN/VPN | Anywhere: your PC, a laptop, a home server behind NAT, a container |

In short: **central has to be reachable from anywhere, a checker does not.**

Multi-node is configured entirely through `config.lua` at the project root. A plain single-node install can ignore it; the behavior only changes when `multi_node = true`.

Copy the config template:

```bash
cp config.lua.example config.lua
```

**Central node:**

```lua
return {
    multi_node = true,
    role = "central",
    logging = { level = "error", output = "file" },
}
```

**Each checker node:**

Set the auth token in an env var (the token comes from central when you add the checker):

`set SPYWEB_UPTYME_CENTRAL_TOKEN=your-token`

```lua
return {
    multi_node = true,
    role = "checker",
    node_name = "checker-fra1",
    central_url = "https://central.example.com",
    auth_token = env_get("UPTYME_CENTRAL_TOKEN"),   -- recommended: keep the secret out of the file, read from env var instead
    central_alert_failures = 3,                     -- failed polls before "central unreachable" fires
    checker_alerts = {
        desktop = true,
        channels = {
            { type = "ntfy", config = { url = "https://ntfy.sh", topic = "uptyme-checker" } },
        },
    },
}
```

**Connecting a checker:**

1. On central, open **Nodes → Add Node** and copy the generated token. (It's shown once; you can reset it later from the node's detail panel.)
2. Put that token in the checker's `config.lua` (or in the `SPYWEB_UPTYME_CENTRAL_TOKEN` environment variable) and start the checker.
3. The checker registers itself on first start and remembers its node ID. After that it polls central every **10 seconds**, picking up monitor changes automatically.

Checkers do not send their own per-monitor alerts - they only report. Monitor alerts are generated by central.

**A checker's UI is read-only.** It shows a badge next to the logo and only the Monitors page; creating, editing and deleting are disabled there, and Settings, Notifications, Status Pages and Nodes are hidden. (This assumes the server is running; if you start a checker with `--no-server` as recommended under [Reachability](#reachability), there is no UI at all.)

## Consensus

Central marks a monitor **DOWN** when enough live nodes report it down:

```
threshold = min(consensus_min_nodes, ceil(live_nodes × consensus_quorum_pct ÷ 100))
```

- **live_nodes** are nodes that reported within `node_liveness_sec` (default 90s). Central counts as one of them.
- `consensus_min_nodes` and `consensus_quorum_pct` are capped against each other, so it is not purely a minimum-node count: with the defaults (`2`, `51%`), one live node reporting down meets the threshold (`1`) and central flips to DOWN; with two live nodes the threshold is `2`, so both must agree.
- Every consensus transition is what generates the cluster alert ("Cluster consensus: 2/3 nodes report DOWN") and what shows up in the dashboard's incident list.

Tune these in [Instance Settings](README.md#instance-settings) on the central node if you see too much noise or too little sensitivity.

## Reachability

Checkers always dial **out** to central - central never connects to a checker. Everything about cluster networking follows from that one direction.

**Central must be reachable by every checker.**

- A checker reaches central at whatever you put in its `central_url`. For a distributed cluster that's usually a public address - a VPS or a server with an open port / reverse proxy.
- SpyWeb binds to `127.0.0.1` only by default, so you must deliberately expose it - reverse proxy, tunnel, or an open port - and `central_url` must point at how checkers reach it. See the deployment steps below.
- **Set `SPYWEB_API_KEY` before exposing central.** Checkers authenticate with their node tokens, but the admin API needs the key. See [Securing an exposed central](#securing-an-exposed-central).
- This requirement is *"reachable by the checkers"*, not *"public"*: if every checker shares a private network with central (LAN, WireGuard/Tailscale, or a cloud VPC), point `central_url` at the private address and expose nothing to the internet.

**Deploying central.** Central is an ordinary always-on web service, so deploy it exactly as the SpyWeb **[Deployment guide](https://docs.spyweb.app/api-and-server/deployment/)** describes - it walks through the systemd unit, setting `SPYWEB_API_KEY`, and every way to expose the server (SSH tunnel, nginx or Caddy reverse proxy, UFW whitelist). A reverse proxy is the usual pick for a cluster: checkers get TLS and a stable hostname instead of a bare `ip:port`. The only cluster-specific steps the guide doesn't cover are to expose the port so **checkers** can reach it, and to point every checker's `central_url` at that exposed address.

### Securing an exposed central

An exposed central carries two planes, and only one of them is for checkers:

| Plane | Who calls it | Auth |
|---|---|---|
| `/api/v/*` (admin API + dashboard data) | You | `SPYWEB_API_KEY` via `X-SpyWeb-Key` |
| `/api/public/*` | Checkers | Per-node token (`x-uptyme-checker-token`) |

- **You can keep `/api/v/*` off the public internet, if you want.** Checkers never call it - it exists only for you. Restrict it at the reverse proxy, as below. Rate limits slow brute force down but are not a reason to leave the admin plane open.
- **Use a long random key:** Node tokens carry a 256-bit random secret; the admin key is whatever you typed, so length is the whole defense.
- **Rotate it occasionally** and immediately if you think it leaked. It is cheap: new env var, restart, re-enter the key in the dashboard. Checkers are unaffected - they never see `SPYWEB_API_KEY`.
- **`/api/public/*` is fine as-is.** Every cluster route verifies the node token (SHA-256-hashed at rest, revocable per node from the Nodes page, `401` otherwise), reports are rate-limited per node, and the only keyless route is published status pages, which are read-only.
- The index stays open on purpose: the same SPA serves published status pages at `/status/...`, and the static shell contains no data - everything it shows lives behind `/api/v/*`.

**nginx** - add to your existing `server {}` next to your proxy config:

```nginx
location /api/v/ {
    allow 203.0.113.7;   # your admin IP(s); repeat the allow line for more
    deny  all;
    proxy_pass http://127.0.0.1:7979;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

`/api/public/` needs no restriction - checkers come and go from anywhere.

**Caddy** - one matcher above your existing `reverse_proxy`:

```caddy
@adminapi {
    path /api/v/*
    not remote_ip 203.0.113.7
}
respond @adminapi 403

reverse_proxy localhost:7979
```
- **Symptom to know:** a restricted IP shows up as a `Blocked (HTTP 403)` toast while the dashboard stays empty, and the login dialog shows the same line if you submit a key. That means your IP fell off the allowlist.
- If your admin IP changes (a dynamic home IP, for example), allow a CIDR or a tunnel IP instead, or keep admin access on WireGuard/SSH and skip public `/api/v/*` entirely.

**A checker needs none of that - just the [Install](README.md#install) guide.**

- Copy the checker `config.lua` above, start it, and you're done. Nothing to deploy, no proxy, no exposure - every connection goes outward.
- It needs **outbound** access only - to central and to the targets it probes. No public IP, no open port, no port forward, and no firewall changes are required to run one.
- That's why a checker is happy on your own PC, a laptop that roams between networks, a home server behind NAT, or a container.
- Skip the dashboard/API server entirely, since nothing ever connects to a checker:

  ```bash
  ./spyweb start --no-server
  ```

  `SPYWEB_DISABLE_SERVER=1` is the environment-variable equivalent, which is handy in a systemd unit. With the server off there's no local UI either - if you want one for debugging, start the checker normally instead and leave it bound to `127.0.0.1`.
- If a checker can't reach central, it retries and alerts after `central_alert_failures` consecutive failed polls (default 3, roughly 30 seconds).
